## #76 今日日程的执行队列与观测

- **状态**：Done
- **初评**：7.7（正确性 7.2，健壮性 7.1，准确性 7.2，完整性 8.2，可维护性 7.3，简洁性 7.4，一致性 8.0，惊喜度 7.5，可用性 8.4，交互体验 8.1），详见 [初评报告](eval/reports/2026-10-25-76-execution-queue-review.md)。

- **背景**：现有「今日日程」可展示当前/下一项并记录完成或跳过，但执行中缺少开始、跳转等过程观测，也无法从事件进行日对账。原始需求见 [设计文档](design/2026-10-24-76-execution-queue.md)。
- **方案**：沿用现有日程及其计划顺序，在执行过程中加入动作记录、积分、对账和轻量出口。日程编辑、模板和当天计划的配置保持现状；每个子任务可单独裁剪，组合时仅需保留其列明的依赖。被裁剪的子任务不计入父任务验收。
- **分析**：#76.2 基于现有日程提供动作事件；#76.3–#76.5 可按需组合，#76.6 是手机入口。现有时间轴、跨午夜、模板快照及手动推进语义应保留。
- **验收**：保留的子任务各自通过验收，现有日程及项目注意力引导无回归；完整组合时可完成设计文档首页全部验证场景。

### #76.2 动作日志与积分

- **状态**：Done
- **初评**：7.2（正确性 7.2，健壮性 7.1，准确性 7.2），详见 [初评报告](eval/reports/2026-10-25-76-execution-queue-review.md)。

- **后续优化**：积分可见、按计划时间段跳转免扣和标准分见 #81。
- **规则修订**：仅当前项可完成，完成分值由计划时间段判定，见 #82；旧完成事件保留原分值。
- **分组**：#76 今日日程的执行队列与观测

- **方案**：基于已保存的日程顺序，当前项首次在可见页面展示时自动记录开始；在当前项保留完成、跳过、暂离等局部操作，顶部首位提供「跳转日程」下拉列表。停留在当前项无需主动标记拖延。保存不可改写的动作事件；完成分值按 #82 的计划时段规则，跳过 −3；按 #81 的规则，跳到目标项原计划时间段内记 0 分，其余跳转扣 3 分。运行时跳转不改写日程项或模板。
- **验收**：每个动作留下正确事件与分数；当前项自动开始且刷新不重复记开始事件；下一项须跳转后才能完成，重复请求不重复记分；执行偏离不改动已保存的日程配置；刷新及重启后记录保留，写入失败不显示成功。
- **AI 自动验证**：`make test`、`make build`、`make vet` 通过；日程单测覆盖计划时段、跳转、重复动作和非法跨项完成，API 测试覆盖重复提交与持久化。

- **预期结果**：动作日志和积分与设计一致，已保存的日程项及模板未改变。
- **最小回传**：与其余 #76 子任务合并试跑后，回复「#76 已通过」。

## #77 日程执行计时准确性

- **状态**：Done
- **分组**：#76 评估衍生
- **背景**：跳转日程后原项开始时间仍有效，之后完成原项时会把处理其他项的时间一并计入；日对账累计计时可能重叠。自动开始写入失败后，当前页面也不会再次尝试记录开始。
- **方案**：跳转和暂离时结束当前计时片段，回到原项时自动重新开始；完成时累计该项有效片段，面板显示同一累计口径。开始请求失败后允许下一次读取重试。
- **验收**：跳转和暂离期间不计入原项耗时，返回后继续累计；日对账总耗时与完成事件一致，旧记录仍可读取。
- **评估**：8.4。服务端持久事件与前端显示口径一致，跳转、返回和暂离有定向回归；自动开始依赖页面可见和后续读取，仍属观测计时而非实际专注计时。
- **AI 自动验证**：`go test ./internal/schedule`、`make test`、`make vet`、`pnpm run build`、`node --test tests/schedule-panel.test.mjs` 通过。
- **影响**：当日耗时可能高估或缺失，影响 #76.2 与 #76.3 的数据可信度。
- **严重程度**：中等。
- **来源**：[验收后评估](eval/reports/2026-10-25-76-execution-queue-review.md)。

### #80.2 异步刷新与缓存回显

- **状态**：Done
- **分组**：#80 Dashboard 信息架构与刷新体验
- **背景**：当前 Dashboard 请求会扫描多个 Agent 来源，首次加载使用明显的 Loading；请求失败时前端清空已有结果。
- **需求**：页面刷新后的首次请求携带「首次」标识，后端先返回与当前筛选条件相符的上次成功结果；前端立即展示该结果，再异步拉取一次新结果。日常轮询和手动刷新保持当前内容可读，不用明显的全页 Loading。
- **验收**：有缓存时首屏先显示旧结果及其更新时间，随后无闪屏更新；不同筛选条件不串数据；新请求失败时旧结果仍可读并有错误提示。
- **决策**：采用进程内最近一次结果缓存；服务冷启动或筛选条件不同则执行真实扫描，不写缓存文件。
- **方案**：首次请求携带首次标识，服务端按有效扫描参数与设置版本匹配缓存，命中时返回旧结果及命中标识；前端先展示并异步请求新结果。手动与定时刷新保持现有数据，错误只更新提示，并防止过期请求覆盖新数据。
- **评估**：8.2。缓存键隔离筛选条件，前后端均防止旧请求覆盖新结果；冷启动仍需等待真实扫描，符合已选范围。
- **AI 自动验证**：Dashboard API 缓存命中/隔离测试、前端缓存回显/错误保留/请求乱序测试、Go 测试及前端构建通过。

- **决策**：采用日程区域内可见积分，不放 Dashboard 全局标题栏。命中目标项“计划开始至专注加休息结束”的区间时，跳转计 0 分；计划空档不匹配任何项。

## 产品定位决策

**从**：多 Agent 会话的状态查看工具
**到**：多 Agent 会话的注意力管理与调度工具，让用户能快速判断下一步该关注哪一路 Agent。

核心 workflow：启动 Agent → 自动发现会话 → 按项目归类 → Dashboard 汇总状态 → 用户依据提醒和建议进行关注、授权或切换。

**主动不做的事**：

- 不替代 Claude Code、Hermes 或其他 Agent 的对话和执行能力。
- 不自动替用户批准高风险操作。
- 不在 Dashboard 中复制完整的 Agent 工作界面。

## 拒绝清单

- 以独立项目 ID/名称实体替代“路径即项目”模型。
- 通过抓取终端渲染内容承载所有 Agent 状态，优先使用稳定的 JSON 或明确命令输出。
- 在 pflow 内自建 WebSocket + PTY 桥接，优先复用成熟的 ttyd + tmux 链路。
