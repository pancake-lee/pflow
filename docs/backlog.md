## 终端交互

### #65 Codex 原生鼠标滚动被 tmux 复制模式截获

- **状态**：Done。
- **分组**：终端交互
- **背景**：用户反馈新版 Codex 自行处理鼠标滚动，使用 pflow 托管后向上滚动进入 tmux 复制模式，无法浏览 Codex 会话旧内容。
- **分析**：2026-10-13 检查发现 `~/.tmux.conf` 及当前 tmux server 的 root 键表均存在无条件进入复制模式的 WheelUpPane 自定义绑定。当前 `pflow-pflow-codex` 窗格的 `mouse_any_flag=1`、`alternate_on=1`，应用已启用鼠标事件接收。pflow 的会话启动代码没有配置滚轮绑定；此次冲突来自用户 tmux 规则。tmux 官方支持根据应用鼠标状态转发原始事件，参见 [官方配置示例](https://github.com/tmux/tmux/wiki/Recipes#send-up-and-down-keys-for-the-mouse-wheel)。
- **方案**：2026-10-14 用户选择 B。由 pflow 调用 tmux 公开命令，在运行时为托管会话启用专用键表及鼠标接收。复制既有 root 键表中的快捷键与鼠标操作，仅替换上下滚轮分发：应用开启鼠标或窗格处于复制模式时转发原始事件，否则向上滚动进入 tmux 复制模式。前缀键表与其他会话的 root 键表保持原样。新建、重新接入及 Web 终端接入统一应用策略；不修改 `~/.tmux.conf`，不新增依赖。
- **任务列表**：
  - [x] 用户选择运行时配置托管会话专用键表。
  - [x] 按所选范围修复滚轮事件分发，上下滚动均兼容应用鼠标处理与复制模式。
  - [x] AI 核对配置及事件分发规则，再交付真实终端滚动验收。
  - [x] （用户）在现有 Codex 会话滚动查看旧内容，确认普通终端滚动仍符合预期。
- **验收**：Codex 接收原始滚轮事件并能浏览旧内容；应用未启用鼠标时保留 tmux 历史滚动；已有复制模式仍能滚动；无需重启 Codex 或销毁现有会话。
- **实施记录**：2026-10-14 在会话管理器中通过公开 `list-keys` 命令复制 root 绑定，使用标准 `source-file` 命令从 stdin 加载到托管会话共用的 `pflow-root` 专用键表。仅改写绑定目标表与上下滚轮规则，启用会话级 mouse/key-table 选项。启动器的新建与重连、普通终端创建及 Web 终端接入均使用同一配置逻辑。再次接入时刷新 root 快捷键快照，清除已删除的旧绑定；前缀键与复制模式键表保留原样。中英文 README 及技术说明已同步，未修改真实 tmux server 或用户配置文件。
- **AI 自动验证**：`go test ./...`、`go vet ./...`、`make build`、`git diff --check` 通过，产物为 `bin/pflow`。隔离 tmux 集成测试覆盖 root/prefix 不变、非托管会话 mouse/key-table 不变、带引号及重复属性的快捷键复制、重新配置清除旧快捷键和会话不存在错误；Python 标准库 PTY 测试实际发送上下滚轮、普通文本、自定义 F12、复制模式滚动和前缀分离事件，全部通过。测试 server 使用独立 socket，并在退出时执行 `kill-server` 清理。构建仅有既存前端 chunk 大小提示。

## 产品定位决策

**从**：多 Agent 会话的状态查看工具
**到**：多 Agent 会话的注意力管理与调度工具，让用户能快速判断下一步该关注哪一路 Agent。

核心 workflow：启动 Agent → 自动发现会话 → 按项目归类 → Dashboard 汇总状态 → 用户依据提醒和建议进行关注、授权或切换。

**主动不做的事**：

- 不替代 Claude Code、Hermes 或其他 Agent 的对话和执行能力。
- 不自动替用户批准高风险操作。
- 不在 Dashboard 中复制完整的 Agent 工作界面。

## 拒绝清单

- 以独立项目 ID/名称实体替代“路径即项目”模型。
- 通过抓取终端渲染内容承载所有 Agent 状态，优先使用稳定的 JSON 或明确命令输出。
- 在 pflow 内自建 WebSocket + PTY 桥接，优先复用成熟的 ttyd + tmux 链路。
