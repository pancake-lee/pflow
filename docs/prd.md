# PRD: pflow — 多 Agent 会话的注意力管理与调度工具

## 1. 产品定位

pflow 是一个**注意力管理工具**，帮助用户在同时使用多个 AI 编程 Agent（Claude Code、Hermes 等）时，降低多任务切换的心智负担。

类比：不是"遥控指挥部"（坐在后方远程操控），而是**"战报 + 传令系统"**——军帐中看各部战况，需要时**亲临前线**拔刀参战。

> **核心理念**：pflow 不替代用户的工作软件。用户在 Dashboard 看到状态信息后，自己切换到 VSCode、终端或其他工具去操作。pflow 的职责是**呈现信息、辅助决策**，而不是在工具内嵌入另一个工具。

## 2. 解决的问题

### 2.1 现状痛点

- 多个 Agent 并行工作时，用户需要逐个窗口查看"有没有在等我"
- Agent 执行任务期间的等待时间被低效消耗（刷手机、走神）
- 当某个 Agent 需要用户确认（如授权工具调用）时，用户无法及时感知
- 在多个项目/Agent 之间切换没有引导，靠用户自己记忆和判断

### 2.2 核心价值

| 痛点 | 解决方案 |
|------|---------|
| 不知道哪个 Agent 在等我 | 红绿灯状态仪表盘（🟢交战中 / 🟡待命 / ⚪休整） |
| 等待时间被浪费 | 主线/支线策略引导用户注意力分配到合适的项目 |
| 切换上下文损耗大 | 以项目为维度组织会话，用户自然判断切换时机 |
| 无法快速了解全局 | Dashboard 聚合所有项目下的 Agent 状态，一目了然 |

## 3. 用户角色与交互模型

### 3.1 角色定位：统帅的三种姿态

用户不是被"钉死"在固定层级的角色，而是可以**随时切换指挥姿态**：

- **统帅视角（军帐）**：看全局战报，调动各部兵力，定战略方向
- **将领视角（阵前）**：指挥某路兵马（Lead Agent）如何协调子任务
- **战士视角（前线）**：亲自提刀上阵，与具体 Agent 对话解决具体问题

### 3.2 核心交互循环

```
用户设定主线/支线项目策略
       ↓
各路 Agent 在各项目中出战
       ↓
Dashboard 按项目聚合展示状态
       ↓
用户看 Dashboard → 判断：
  ├── 主线项目有 Agent 在等待 → 切换到该项目的终端/VSCode
  ├── 支线项目有进展 → 快速浏览后继续主线
  └── 调整策略（升降级项目优先级）
       ↓
处理完毕 → 回到 Dashboard 或继续工作
```

### 3.3 关键设计原则

- **最好的设计应该是无感的**：pflow 是信息层，不替代用户已有的工作软件（终端、VSCode 等）。用户看 Dashboard 获取信息，然后自己决定何时切换回工作环境。"亲赴前线"是用户的自然行为，不需要 pflow 提供按钮或内嵌终端来完成。
- **统帅保留兵权**：系统只做军情分析和建议，不自动调兵
- **尊重主攻方向**：主攻进行中不打扰，支线军情待战罢再报
- **信息聚合优于功能堆叠**：Dashboard 的核心价值是让用户快速判断"现在该关注哪个项目"，而非在 pflow 中完成所有操作

## 4. 核心概念

### 4.1 项目（Project Root）

pflow 不引入独立的"项目"实体。**路径即项目**——session 元数据中已有的 working directory 就是天然的归属标识。

用户只需标记"哪些目录是项目根"（勾选 ☐ "识别为项目"），系统自动将工作目录匹配的 session 归入对应项目：

- session 的 cwd 是 `/home/user/code/pflow/internal/api`
- 用户标记了 `/home/user/code/pflow` 为项目根
- → 该 session 自动归入 `pflow` 项目

**匹配规则**：最长前缀匹配。如果 `/a` 和 `/a/b` 都是项目根，`/a/b/c` 下的 session 归入 `/a/b`（更具体的匹配）。

**根目录保护**：`/` 不能被标记为项目根，防止所有 session 被错误归入同一个项目。

**零手动归类**：用户不需要创建项目、命名、或手动把 session 拖到某个项目下。标记项目根是唯一的操作。

| 优先级 | 说明 | 数量限制 |
|--------|------|---------|
| **主线项目 (Primary)** | 今日最高优先级，用户的主要精力投入方向 | 1 个 |
| **支线项目 (Secondary)** | 今日次优先级，可在等待间隙推进 | 最多 3 个 |
| **普通项目 (Normal)** | 其他需要关注但不紧急的项目 | 不限 |

### 4.2 Agent Session（一支部队）

一个 Agent Session 代表一个正在执行任务的 AI Agent 实例，归属于某个项目：

- **兵种**：Claude Code CLI / Hermes / Cline（VSCode）/ API 直接调用 / 其他第三方 Agent
- **三态**：🟢 交战（busy/running） / 🟡 待命（waiting） / ⚪ 休整（idle） / ⚫ 静默（inactive）

### 4.3 军情哨（Attention Manager）

系统的核心调度逻辑——不是另一个 Agent，而是**规则引擎 + LLM 分析调用**：

- 输入：各部战况、主线/支线配置、时间预算、统帅偏好
- 输出：时机合适的军情汇报（何时转场、转向哪里）
- 决策维度：Agent 等待时间、项目优先级、估计耗时、用户当前精力

### 4.4 战局图（Quest Graph）

可选的高级功能——描述战场之间的依赖和并行关系：

- 主攻方向、侧翼战场、钳制关系、合围检测

### 4.5 军帐战报（Dashboard）

以项目为维度的两级结构：项目 → 会话。

```
┌───────────────────────────────────────────────────────┐
│  ⭐ 主线项目 (1)                                       │
│  ┌──────────────────────────────────────────────────┐ │
│  │ 🚀 pflow                                         │ │
│  │   ├─ [🟢] claude (c50e1b2e)  last: 2min ago     │ │
│  │   └─ [⚪] claude (a3b2c1d4)  last: 10min ago    │ │
│  └──────────────────────────────────────────────────┘ │
│                                                       │
│  🚩 支线项目 (3/3)                                    │
│  ┌──────────────────────────────────────────────────┐ │
│  │ 📝 周报                                          │ │
│  │   └─ [🟡] claude (d4e5f6a1)  last: just now     │ │
│  └──────────────────────────────────────────────────┘ │
│  ...                                                  │
│                                                       │
```

## 5. 分阶段计划

### 阶段一：可行性验证 ✅ 已完成

**目标**：验证核心假设——能否获取 Claude Code 等 Agent 的对话状态和对话内容，并聚合成可用的仪表盘。

| 功能 | 说明 |
|------|------|
| `pflow probe` | 探测一个正在运行的 Claude Code 会话，输出其状态快照 |
| `pflow status` | 列出本地所有已知 Agent 会话的状态表（CLI 文本表格） |
| Dashboard API | HTTP 端点返回所有 session 的 JSON 状态快照 |
| 双 Agent 支持 | Claude Code + Hermes 统一展示 |

### 阶段二：Web Dashboard ✅ 已完成

**目标**：构建浏览器端可视化面板，用 Vue 3 + Naive UI 提供"军帐战报"。

| 功能 | 说明 |
|------|------|
| Web 战况面板 | 浏览器访问 `http://localhost:8080`，红绿灯状态表 + 筛选 + 自动刷新 |
| 会话详情 | 点击展开/侧边抽屉查看完整 session 信息 |
| 单文件部署 | Vue SPA 打包嵌入 Go binary，`pflow serve` 一个命令启动全部 |
| `pflow claude` | 创建 tmux + Claude 托管会话，statusline 自动关联 Dashboard |
| Web 终端（辅助） | ttyd + tmux 提供 Dashboard 内终端交互能力，但非主要交互路径 |

### 阶段三：项目策略管理 ← 当前阶段

**目标**：从"扁平 session 列表"升级为按项目路径分组的两级视图，让 Dashboard 真正成为注意力分配的决策辅助工具。

**设计原则**：路径即项目。不引入独立的项目 ID/名称实体，直接用 session 已有的 working directory 作为归属标识。用户只需标记"哪些路径是项目根"，子目录 session 自动归入。

| 功能 | 说明 |
|------|------|
| 项目根标记 | `~/.pflow/project_roots.json` 存储被标记为项目根的路径列表 + 优先级 |
| Session 自动归类 | 按最长前缀匹配：session 的 cwd 匹配到某个项目根路径，自动归入 |
| 主线/支线策略 | 用户设定 1 个主线 + 最多 3 个支线，其余为普通 |
| Dashboard 视图重构 | 前端按项目根分组展示 session，按优先级分区（主线/支线/普通/未归类） |
| "识别为项目" ☐ | 界面上每个 distinct 工作目录旁提供勾选框 + hover tooltip，一键标记/取消 |
| 根目录保护 | `/` 不能被标记为项目根 |

### 阶段四：智能调度

| 功能 | 说明 |
|------|------|
| 沉默提醒 | 主线项目 Agent 沉默超阈值时通知用户 |
| 军情哨主动推送 | 定时 + 事件触发，主动提醒用户关注某个项目 |
| 统帅偏好学习 | 根据用户的历史选择，自动调整推送频率和时机 |

### 阶段五：体验层

| 功能 | 说明 |
|------|------|
| TUI Dashboard | 基于 Bubble Tea 的终端可视化战报 |
| 游戏化外壳 | 战场地图隐喻的视觉包装 |
| 跨设备同步 | 手机/平板查看状态 |

## 6. 非功能需求

- **平台**：Linux / macOS 优先，Windows 后续评估
- **语言**：Go（CLI 工具）+ Vue 3 / TypeScript（Web Dashboard）
- **协议**：MIT License
- **依赖**：最大程度复用成熟开源组件，不自研 Agent
- **设计原则**：最好的设计应该是无感的——pflow 是信息层，不替代用户已有的工作软件
