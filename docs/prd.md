# PRD: pflow — 多 Agent 会话的注意力管理与调度工具

## 1. 产品定位

pflow 是一个**注意力管理工具**，帮助用户在同时使用多个 AI 编程 Agent（Claude Code、Cline、Codex CLI 等）时，降低多任务切换的心智负担，在合适的时机被引导到合适的 Agent 会话。

类比：不是"遥控指挥部"（坐在后方远程操控），而是**"战报 + 传令系统"**——军帐中看各部战况，需要时**亲临前线**拔刀参战。

## 2. 解决的问题

### 2.1 现状痛点

- 多个 Agent 并行工作时，用户需要逐个窗口查看"有没有在等我"
- Agent 执行任务期间的等待时间被低效消耗（刷手机、走神）
- 当某个 Agent 需要用户确认（如授权工具调用）时，用户无法及时感知
- 在多个项目/Agent 之间切换没有引导，靠用户自己记忆和判断

### 2.2 核心价值

| 痛点 | 解决方案 |
|------|---------|
| 不知道哪个 Agent 在等我 | 红绿灯状态仪表盘（🟢交战中 / 🟡待命 / ⚪休整） |
| 等待时间被浪费 | 军情哨主动推送合适的"侧翼任务" |
| 切换上下文损耗大 | 传令兵式引导对话，帮用户做出切换决策 |
| 无法快速进入 Agent 会话 | 一键唤起终端或打开 VSCode |

## 3. 用户角色与交互模型

### 3.1 角色定位：统帅的三种姿态

用户不是被"钉死"在固定层级的角色，而是可以**随时切换指挥姿态**：

- **统帅视角（军帐）**：看全局战报，调动各部兵力，定战略方向
- **将领视角（阵前）**：指挥某路兵马（Lead Agent）如何协调子任务
- **战士视角（前线）**：亲自提刀上阵，与具体 Agent 对话解决具体问题

### 3.2 核心交互循环

```
用户设定今日主攻方向 / 侧翼战场
       ↓
各路 Agent 出战（用户自由工作或等待）
       ↓
军情哨监控各部战况
       ↓
触发条件满足 → 传令兵来报 → 用户选择：
  ├── 亲赴前线（唤起 Agent 会话）
  ├── 稍后再报
  └── 知道了
       ↓
处理完毕 → 返回军帐或继续巡营
```

### 3.3 关键设计原则

- **统帅保留兵权**：系统只做军情分析和建议，不自动调兵
- **渐进式介入**：先看战报（Dashboard），再决定是否亲赴前线（attach）
- **尊重主攻方向**：主攻进行中不打扰，侧翼军情待战罢再报
- **入口自由**：用户可自选终端、VSCode 或其他方式进入 Agent 会话

## 4. 核心概念

### 4.1 Agent Session（一支部队）

一个 Agent Session 代表一个正在执行任务的 AI Agent 实例：

- **兵种**：Claude Code CLI / Cline（VSCode）/ API 直接调用 / 其他第三方 Agent
- **三态**：🟢 交战（busy） / 🟡 待命（waiting） / ⚪ 休整（idle）

### 4.2 军情哨（Attention Manager）

系统的核心调度逻辑——不是另一个 Agent，而是**规则引擎 + LLM 分析调用**：

- 输入：各部战况、主攻方向、侧翼配置、时间预算、统帅偏好
- 输出：时机合适的军情汇报（何时转场、转向哪里）
- 决策维度：Agent 等待时间、任务优先级、估计耗时、用户当前精力

### 4.3 战局图（Quest Graph）

可选的高级功能——描述战场之间的依赖和并行关系：

- 主攻方向、侧翼战场、钳制关系、合围检测

### 4.4 军帐战报（Dashboard）

```
┌─────────┬─────────┬──────────┬──────────┐
│ 部队    │ 战场    │ 战况     │ 行动     │
├─────────┼─────────┼──────────┼──────────┤
│ a-001   │ 项目A   │ 🟢 交战中 │ -        │
│ a-002   │ 项目B   │ 🟡 待命  │ [赴前线] │
│ a-003   │ 项目C   │ ⚪ 休整  │ [出战]   │
└─────────┴─────────┴──────────┴──────────┘
```

## 5. 分阶段计划

### 阶段一：可行性验证 ✅ 已完成

**目标**：验证核心假设——能否获取 Claude Code 等 Agent 的对话状态和对话内容，并聚合成可用的仪表盘。

#### 对用户可见的功能

| 功能 | 说明 |
|------|------|
| `pflow probe` | 探测一个正在运行的 Claude Code 会话，输出其状态快照（存活/忙/等待、当前操作摘要、上下文用量） |
| `pflow status` | 列出本地所有已知 Agent 会话的状态表（CLI 文本表格） |
| Dashboard API | HTTP 端点返回所有 session 的 JSON 状态快照，供后续 TUI/Web 界面消费 |

#### 验证项

| 验证项 | 通过标准 |
|--------|---------|
| 捕获 Claude Code 的输出流 | 拿到完整的纯文本输出 |
| 推断 busy/waiting/idle 三态 | 准确率 > 80% |
| 感知"等待用户确认"事件 | 识别率 > 70% |
| 实时读取对话内容摘要 | 拿到最近 N 轮对话的文本 |
| 多 Agent 同时监控 | 无冲突、无串扰 |

#### 不包含

- 引导建议推送
- 注意力配置
- 主动提醒
- 可视化界面（Web Dashboard 推迟到阶段二）

### 阶段二：Web Dashboard ← 当前阶段

**前提**：阶段一验证通过，Dashboard API 已可用。

#### 对用户可见的功能

| 功能 | 说明 |
|------|------|
| Web 战况面板 | 浏览器访问 `http://localhost:8080`，红绿灯状态表 + 筛选 + 自动刷新 |
| 会话详情 | 点击展开/侧边抽屉查看完整 session 信息 |
| 单文件部署 | Vue SPA 打包嵌入 Go binary，`pflow serve` 一个命令启动全部 |

#### 技术选型

Vue 3 + Naive UI + TypeScript + Vite。详见 [`tech.md`](./tech.md) 第 5.2 节。

#### 不包含

- Agent 启动/停止/attach（后端能力，留待后续）
- 军情哨推送（留待阶段三）
- 游戏化外壳（留待阶段四）

### 阶段三：核心 MVP（CLI 能力扩展）

| 功能 | 命令 | 说明 |
|------|------|------|
| ✅ 启动 Claude 托管会话 | `pflow claude [-dir] [-name]` | 创建 tmux session + 启动 Claude，自动配置 statusline 关联 Dashboard |
| 亲赴前线 | `pflow attach <session>` | 唤起终端（tmux attach）或打开 VSCode，直接与 Agent 交互 |
| 手动获取建议 | `pflow suggest` | 军情哨分析当前所有会话状态，给出一条引导建议 |
| 设定主攻/侧翼 | `pflow focus --main A --side B,C` | 设定今日主攻方向和可填充的侧翼战场 |
| 沉默提醒 | — | 会话沉默超阈值时终端输出通知 |
| 会话持久化 | — | 断开 SSH / 关闭终端后 Agent 继续在后台工作 |

### 阶段四：智能调度

| 功能 | 说明 |
|------|------|
| 军情哨主动推送 | 定时（如每 5 分钟）+ 事件触发（Agent 状态变化），主动通知用户 |
| 统帅偏好学习 | 根据用户的历史选择（接受/忽略/稍后），自动调整推送频率和时机 |
| 战局图 | 用户手动建立任务依赖关系，系统自动检测阻塞并建议调度 |

### 阶段五：体验层

| 功能 | 说明 |
|------|------|
| TUI Dashboard | 基于 Bubble Tea 的终端可视化战报，实时刷新 |
| 游戏化外壳 | 战场地图隐喻的视觉包装 |
| VSCode 扩展 | 在 IDE 内直接查看和管理 Agent 会话 |
| 跨设备同步 | 手机/平板查看状态、点批准 |

## 6. 非功能需求

- **平台**：Linux / macOS 优先，Windows 后续评估
- **语言**：Go（CLI 工具，与底层 Agent 进程管理技术栈一致）
- **协议**：MIT License
- **依赖**：最大程度复用成熟开源组件，不自研 Agent
