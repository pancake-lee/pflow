# AI 评估模式操作指南

> 本文档是 `work-modes.md` 评估模式的补充，定义 AI 如何按维度评分、收集证据和输出报告。
> 评估器是“判卷老师”：只判断好坏，不提出解决方案。

## 评分标准速查

各维度 1–10 分：

- **10**：无可挑剔，满足要求并有超出预期的亮点。
- **8–9**：良好，主要要求和边界均满足，仅有小改进空间。
- **6–7**：可接受，核心功能可用但存在明显技术债或覆盖不足。
- **4–5**：不足，存在影响使用的功能或质量问题，需要返工。
- **1–3**：严重缺陷，核心功能不可用、安全风险高或未实现设计预期。

## 评分维度

### 代码质量

- **正确性**：是否实现设计方案的预期行为，边界情况如何。
- **健壮性**：错误处理、空值防护、进程退出、文件损坏和并发路径覆盖情况。
- **可维护性**：命名、结构、注释、模块边界和编码规范一致性。
- **简洁性**：是否存在冗余代码、过度抽象或 dead code。

### 功能效果

- **准确性**：session 状态、项目归类、提醒分数和建议是否符合预期。
- **完整性**：核心场景、Agent 类型、异常路径和空状态是否覆盖。
- **一致性**：CLI、API、Dashboard 和持久化状态是否一致。

### 用户价值

面向用户的功能必须从用户视角评估，而不只验证格式：

- **惊喜度**：是否揭示用户自己不容易发现的关联或行动方向。
- **可用性**：用户能否直接据此采取行动，是否需要大量二次加工。
- **交互体验**：等待、加载、错误反馈、状态反馈和结果扫读是否顺畅。
- **AI 增量**：仅对依赖智能分析的功能启用，判断 AI 是否真正增加了价值。

## 评估流程

### 第零步：理解产品定义

1. 读取对应 PRD 章节、设计方案或 backlog 背景。
2. 提炼功能解决的用户问题和提供的价值，作为用户价值评分基准。
3. 若 PRD 缺少功能定义，在评估报告的 findings 中记录。

### 第一步：确认评估目标

1. 明确评估对象：用户指定的功能、代码、PR、提交，或 backlog 中已开发的条目。
2. 读取相关设计、验收条件、编码规范和基线。
3. 确定评分重点：代码质量、功能效果，或两者兼顾。

### 第二步：确认验证条件

根据目标检查服务和依赖是否可用。pflow 的常规验证命令为：

```bash
GOTOOLCHAIN=local make vet
GOTOOLCHAIN=local make test
make build
cd web && npx vue-tsc --noEmit
```

需要真实 tmux、Claude 或 Hermes 环境时，先检查残留进程和环境，再执行手动验收；不为验证长期遗留后台进程。

### 第三步：逐维度评分

1. 使用原始命令输出、测试结果、代码行和实际界面收集证据。
2. 对照评分标准给分。
3. 每个维度列出具体得分点和失分点，不使用无证据的笼统判断。
4. 代码质量评估可用 `git diff HEAD~1` 或 `git show <commit>` 辅助。

### 第四步：输出评估报告

报告写入 `docs/eval/reports/YYYY-MM-DD-<topic>.md`，至少包含：目标、环境、验收项 Pass/Fail、分维度得分、证据、未通过问题和 backlog 链接。需要机器消费时可增加同名 JSON，仅保留结构化字段。

### 第五步：更新文档

- 评估通过（总分 ≥ 6 且没有 1–3 分维度）时，将 backlog 条目标为 Done，并回写实际验证结果。
- 评估不通过时，在 backlog 新增 Pending 条目，只描述问题现象和严重程度，不写方案。
- 首次建立某维度基线时更新 `docs/eval/baseline.md`。
- 验收过程对照验收标准逐项检查，结果回写 backlog 或关联 design 的验收清单；代码可验证项勾选，需部署后验证的标注“需运行时”。

## 评估行为边界

- 评估不修改代码，只收集信息和判断。
- 评估不提出“应该怎么改”，只指出“哪里不够好”。改进方案由规划模式产出。
- 报告只记录实际执行过的命令和结果，不把未执行的检查写成通过。
- 读取配置和数据库时只做必要的只读检查，不写入用户数据，不执行破坏性操作。
