# 文档审阅规范

## 触发条件

- 新一轮功能开发完成、架构或技术栈变化、版本归档、用户主动要求审阅时执行。

## 第一版：文档内部治理

按 `CLAUDE.md` / `AGENTS.md` → `README.md` → PRD → tech → backlog → design → handbook → todo 的顺序检查：

1. 职责越界：文档是否写了别的文档负责的内容。
2. 内容冗余：同一事实是否需要维护多份。
3. 引用失效：相对路径和锚点是否存在。
4. 信息冲突：当前状态、命令、目录和设计是否互相矛盾。
5. 过时残留：已完成或废弃方案是否仍被描述为当前方案。

输出按严重程度列出 `[位置]`、`[问题]`、`[证据]`、`[建议]`，区分可仅凭文档解决的问题和需要源码验证的问题。

## 第二版：源码对齐

从文档声明出发针对性读代码，检查：模块边界、API 路由、数据字段、功能状态、配置路径和构建命令。差异分为：

- L1：文档承诺的架构或功能不存在，或与代码根本矛盾。
- L2：功能存在但文档字段、命令或流程已过时。
- L3：遗漏小功能、示例或边界说明。

L1 需要用户决定改文档还是改代码；L2/L3 可给出推荐修正。

## 归档规则

- 当前有效的产品、架构、设计和验收留在主目录。
- 已完成周期记录、版本说明、一次性审查、重复 TODO 放到 `docs/archive/`，文件名保留日期或原始语义。
- 归档后修复所有入口链接；不要删除历史证据。
- `docs/archive/output/` 等已有产物按原主题保留，不与当前文档混写。
