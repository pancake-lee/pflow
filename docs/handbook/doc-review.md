# 文档审阅规范

> 定期执行文档治理，确保各文档各司其职、不冗余、不越界、与代码实现一致。
> 用户按需触发，每次自行判断采用第一版或第二版。

## 触发条件

- 新一轮功能开发完成后。
- 技术栈或架构发生重大变更后。
- 项目收尾或版本归档阶段。
- 用户主动要求审阅文档时。

## 第一版：纯粹文档整理（不读源码）

**目标**：仅通过文档间交叉比对，找出以下问题：

1. 职责越界：文档包含超出其职责范围的内容。
2. 内容冗余：非 README/CLAUDE/AGENTS 文档重复描述其他文档已详述的内容。
3. 引用失效：文档间引用指向不存在的文件或锚点。
4. 信息冲突：同一事实在不同文档中描述矛盾。
5. 过时残留：已变更的决策或架构仍作为当前状态描述。

**审阅顺序**：`CLAUDE.md` / `AGENTS.md` → README → PRD → tech → backlog → design → handbook → archive。

**审阅后输出**：按类型和严重程度排序的问题清单；每项给出 `[位置]`、`[问题]`、`[证据]`、`[建议]`，并标记哪些问题仅第一版可解决、哪些需要第二版源码验证。

## 第二版：源码对齐（基于文档声明读源码）

**目标**：从第一版问题清单出发针对性阅读源码，找出“文档这么说，但代码实际那样”的差异。不从源码出发反推文档问题，避免全量读源码。

**审阅维度**：

- D1 架构描述 vs 实际代码（模块划分、目录结构）。
- D2 API 契约 vs 实际路由（路径、参数、响应结构）。
- D3 数据模型 vs 实际结构（字段、类型、可空性）。
- D4 功能实现 vs 需求覆盖（产品范围是否有对应代码）。
- D5 配置与部署（命令、路径、默认值是否一致）。

**差异分级**：

- **L1 严重**：文档描述的架构/功能根本不存在，或代码与文档承诺矛盾。
- **L2 中等**：功能存在但文档有过时字段、命令或流程。
- **L3 轻微**：遗漏已实现的小功能、示例或边界说明。

**审阅后输出**：按 L1/L2/L3 分级的差异清单，每项给出 `[文档声明]`、`[源码实际]`、`[差异描述]`、`[建议方案]`。L1 必须提交用户裁决；L2/L3 可给出推荐方案供用户选择或授权直接修改。

## 归档规则

- 当前有效的产品、架构、设计和验收留在主目录。
- 已完成周期记录、版本说明、一次性审查和重复工作材料放到 `docs/archive/`。
- **版本归档必须识别 Done 条目，将其完整信息迁移到版本文档，并从 backlog 的总览和详情中删除，backlog 只保留未完成条目。**
- 归档后修复所有入口链接；不要删除历史证据。
- `docs/archive/output/` 等已有产物按原主题保留，不与当前文档混写。
