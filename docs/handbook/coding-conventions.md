# 编码与验证规范

## 通用

- 代码是实现的唯一真相源；文档描述产品、架构、决策和验收，不复制代码细节。
- Markdown 优先使用标题和列表；只有对比数据或参数时使用表格。
- 设计文档只描述当前方案；被否决的方向记录在对应决策文档或归档参考材料中。
- 新增功能必须说明验证方式；修复 bug 必须覆盖触发它的边界条件。

## Go

- 使用标准格式和命名：包名小写，导出标识符 PascalCase，错误使用上下文包装。
- 修改 Go 后运行 `gofmt`；导出函数和类型写 Godoc 注释。
- 业务逻辑放在对应 `internal/<module>/`，API 和 CLI 主要负责聚合与适配。
- JSON 配置采用临时文件写入后 rename 的原子化模式。
- 不直接执行 `go build`；使用 `make build`，保证前端资源先构建并正确嵌入。
- Go 命令优先设置 `GOTOOLCHAIN=local`，避免隐式下载工具链。
- 不执行危险数据库操作；本项目当前无数据库迁移需求时，不引入破坏性清理。

## Web

- 前端代码位于 `web/`，使用 Vue 3 + TypeScript；优先使用 pnpm，遵守现有 lockfile。
- 修改布局或视觉前先读取 `docs/ui-rules.md`（若该文件存在）；纯逻辑修改无需额外 UI 评审。
- 保持 API 类型、状态展示和后端字段一致；组件逻辑优先抽到 composable，而不是继续扩大单个页面。
- 验证至少执行 `cd web && npx vue-tsc --noEmit`；构建验证使用 `make build`。

## 测试与提交前检查

- 纯逻辑使用 table-driven 单元测试；解析、状态推断、评分和时间边界必须覆盖空输入及异常输入。
- API 变化补充 handler 或集成验证；tmux、Claude、Hermes 依赖真实环境时提供手动验收步骤。
- 最小检查集：`make vet`、`make test`、`make build`。
- 不为验证启动长期服务或写入用户目录，除非测试本身明确需要且可清理。
