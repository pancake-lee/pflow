# 编码与验证规范

> 按语言/模块分节。AI 在对应目录下工作时读取相关节。

## 通用规范

### Markdown 输出

- 减少使用表格，优先使用标题层级（`##` / `###`）+ 无序列表（`-`）组织内容。
- 只有在数据对比、配置参数等真正适合的场景使用表格；长文本不要放入宽表格。

### 文本类文件输出

- 尽量不使用破折号 `--` 或 `——` 展开长句，大部分情况下使用逗号或分句。
- 写文章时避免下定义口吻，去掉绝对化措辞，使用阶段性、有限定的表达。
- 比喻用于辅助理解，不要写成终极结论。

### 文档设计原则

- 设计文档只描述当前方案，设计迭代中的中间产物不留痕迹。
- 经审议明确否决的方向记录到 `docs/archive/` 的决策或参考材料中。
- 设计文档不写“曾考虑 X 但未采用”或“不需要 Y”等否定性叙述。

## Go（cmd/、internal/）

### 命名与结构

- 遵循 Go 标准代码风格，包名使用小写单词，导出标识符使用 PascalCase。
- 列表/切片可使用 `List` 后缀，Map 结构可使用 `Map` 或 `keyToValueMap` 后缀。
- 函数命名优先使用清晰的动宾结构；查询、创建、更新、删除的语义保持一致。
- 业务逻辑放在对应 `internal/<module>/`，API 和 CLI 主要负责聚合与适配。
- 非复杂场景优先使用基础类型组合，仅在复用明显或封装语义明确时抽象新类型。
- 避免在 `if` 中使用分号式短声明，避免形成难读的长代码。

### 格式化与文件

- 修改 Go 后统一执行 `GOTOOLCHAIN=local gofmt -w <file>`。
- 导出的函数和类型需要 Godoc 注释。
- JSON 配置使用临时文件写入后 rename 的原子化模式。
- 不直接执行 `go build`；必须使用 `make build`，确保前端资源先构建并正确嵌入。

### 测试与禁忌

- 核心逻辑、解析、状态推断、评分和时间边界使用 table-driven 单元测试。
- 测试覆盖空输入、异常输入和错误路径；涉及服务行为时补充 handler 或集成测试。
- 测试使用 `defer` 和清理函数移除测试数据，不在测试中修改数据库表结构。
- 不执行危险数据库操作或破坏性清理；不把构建产物写入项目根目录。
- 始终设置 `GOTOOLCHAIN=local`，不依赖自动下载工具链。

## Web（web/）

- 使用 Vue 3 + TypeScript，优先使用 pnpm，并遵守现有 lockfile。
- 修改布局或视觉前先读取 `docs/ui-rules.md`（若存在）；纯逻辑修改无需额外 UI 评审。
- 保持 API 类型、状态展示和后端字段一致；组件逻辑优先抽到 composable，而不是继续扩大单个页面。
- 无需为验证改动启动 Dev Server 并抓取页面；由用户自行启动验证。

## 验证与提交前检查

- 最小检查集：`GOTOOLCHAIN=local make vet`、`GOTOOLCHAIN=local make test`、`make build`。
- 前端逻辑变化补充 `cd web && npx vue-tsc --noEmit`。
- tmux、Claude、Hermes 依赖真实环境时提供手动验收步骤。
- 评估报告只记录实际执行过的命令和结果，不把未执行的检查写成通过。
