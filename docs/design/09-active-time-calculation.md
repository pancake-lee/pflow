# pflow 时间追踪方案 —— 默认方案与 tmux 增强方案

> 本文档描述 pflow 如何计算项目/会话的 TodayMinutes（今日活跃时间），用于注意力失衡检测、高效反馈、主线超时提醒等 suggest 场景。方案采用分层架构：默认方案基于消息估算，无需额外依赖；tmux 焦点事件作为可选的增强方案，在数据可用时自动提升精度。


## 一、问题背景

当前 `TodayMinutes` 的计算方式为 `LastActive - max(FirstActive, 今天 00:00)`，即会话的墙钟跨度。这导致在多任务切换场景下严重高估实际工作时间：

- 用户在项目 A 发了一条消息，切到项目 B 工作，再切回项目 A，两个项目分别显示数小时的活跃时间
- 一个终端开着整天不关，`TodayMinutes` 可能显示 16 小时，实际只工作了 2-3 小时

**影响范围**：注意力失衡（S10）、普通项目超主线（S11）、今日高效反馈（S15）、主线超时提醒（S20）等场景的判断基准全部失效。


## 二、设计目标

1. **默认无依赖**：pflow 核心功能不依赖 tmux 或任何额外基础设施
2. **精度可提升**：当用户通过 pflow 启动 Agent（有 tmux 映射）时，自动使用更精确的追踪方式
3. **自动降级**：任何增强方案失效时，无缝回退到默认方案
4. **用户无感**：所有切换和降级在后台完成，用户不需要配置


## 三、可用数据源分析

### 3.1 Claude Code

| 数据源 | 粒度 | 适用性 |
|--------|------|--------|
| `~/.claude/history.jsonl` | 每条消息一个 entry，含毫秒级 timestamp | ✅ 可用于消息估算 |
| `~/.claude/sessions/<pid>.json` | session 级元数据（status、startedAt、updatedAt） | ⚠️ 仅含状态，不含交互细节 |
| tmux 焦点事件（pflow 注入） | focus-in/focus-out 时间戳 | ✅ 最精确，但需 pflow 启动 |

### 3.2 Hermes（非 weixin）

| 数据源 | 粒度 | 适用性 |
|--------|------|--------|
| `hermes sessions export` | session 级：`started_at`、`last_active`、`message_count` | ✅ 可用于消息估算 |
| `~/.hermes/sessions/sessions.json` | session 级元数据 | ⚠️ 同上 |
| tmux 焦点事件（pflow 注入） | focus-in/focus-out 时间戳 | ✅ 最精确，但需 pflow 启动 |

## 四、分层方案

```
┌─────────────────────────────────────────────────────────────────┐
│  优先级 1：tmux 焦点事件（增强方案）                            │
│  条件：项目有 tmux 映射（通过 pflow 启动）且焦点日志可用        │
│  精度：最高，覆盖阅读/思考/输入全周期                          │
│  失败时 → 自动降级到优先级 2                                   │
├─────────────────────────────────────────────────────────────────┤
│  优先级 2：消息数估算（默认方案）                               │
│  条件：所有 Agent（Claude/Hermes）均适用                       │
│  精度：中等，每条消息估算 3 分钟交互时间                       │
│  数据缺失时 → 自动降级到优先级 3                               │
├─────────────────────────────────────────────────────────────────┤
│  优先级 3：墙钟跨度 × 0.3（最终兜底）                          │
│  条件：新会话或数据损坏                                        │
│  精度：较低，但保证不报错                                      │
└─────────────────────────────────────────────────────────────────┘
```


## 五、默认方案：消息数估算

### 5.1 核心公式

```
TodayMinutes = 项目今日消息数 × 3
```

| 参数 | 默认值 | 说明 |
|------|--------|------|
| `MINUTES_PER_MESSAGE` | 3 分钟 | 每发送一条消息，代表约 3 分钟的交互活动（阅读回复 + 思考 + 编辑 prompt + 发送） |

### 5.2 数据来源

| Agent | 数据源 | 字段 |
|-------|--------|------|
| Claude | `~/.claude/history.jsonl` | 统计今天 `timestamp >= 今日 00:00` 的消息数，按 `sessionId` 或 `project` 归入对应项目 |
| Hermes | `hermes sessions export` 或 `sessions.json` | 使用 `message_count` 字段（需确认是否只含用户消息），按 session 归入项目 |

### 5.3 估算合理性

- **3 分钟/条是“保守”的估算**：一条消息平均对应阅读 Agent 输出（1-2 分钟）+ 思考（1-2 分钟）+ 编辑输入（30 秒），3 分钟是合理的平均值
- **对注意力失衡的判断有效**：不同项目的消息数比例能反映投入时间比例
- **对高效/超时的判断保守**：20 条消息（约 60 分钟）才触发正面反馈，30 条消息（约 90 分钟）才触发超时建议


## 六、增强方案：tmux 焦点事件

### 6.1 原理

通过 tmux 的 `focus-events` 和 `client-focus-in/out` 钩子，在用户终端窗口获得/失去焦点时记录时间戳。

```
tmux 焦点变化 → 记录时间戳 → pflow 读取 → 聚合为“项目活跃时间”
```

焦点事件捕获的时间段，天然包含了用户**阅读输出、思考、移动光标、编辑输入**等所有活动，比仅依赖消息时间戳更准确。

### 6.2 自动注入

pflow 在创建 tmux 会话时自动注入以下配置，用户无需手动设置：

- 开启 `focus-events`
- 设置 `client-focus-in` 和 `client-focus-out` 钩子
- 钩子调用 `tmux-focus-log` 脚本记录事件到 `~/.pflow/focus_history.log`

### 6.3 日志格式

```
<timestamp_ns>|<action>|<session>|<cwd>|<project>|<pid>
```

- `action`：`focus-in` / `focus-out`
- `session`：tmux 会话名（与 pflow 的 containerName 一致）
- `cwd`：当前工作目录
- `project`：从 cwd 提取的项目名

### 6.4 聚合算法

```
1. 获取今天所有 focus-in/focus-out 事件，按时间排序
2. 遍历事件序列：
   a. focus-in（项目 X）→ 开始新活跃段，起始 = 该事件时间
   b. focus-out（项目 X）→ 结束活跃段，段长 = 结束 - 起始，计入项目 X
3. 如果最后一条是 focus-in（未结束）→ 以当前时间为截止，计入该项目
4. 过滤掉 < 10 秒的片段（噪声）
5. TodayMinutes = Σ 各项目所有段长
```

### 6.5 适用条件

| 条件 | 说明 |
|------|------|
| 用户通过 pflow 启动 Agent | 有 tmux 映射，pflow 才能注入配置 |
| 焦点日志存在且包含今天数据 | `~/.pflow/focus_history.log` |
| 焦点日志解析成功 | 格式正确，session 名匹配映射中的 containerName |

## 八、对 suggest 场景的影响

| 场景 | 依赖字段 | 使用方案 |
|------|----------|----------|
| S10 注意力失衡 | 支线 vs 主线 TodayMinutes 比例 | 优先 tmux，否则消息估算 |
| S11 普通项目超主线 | 普通项目 vs 主线 TodayMinutes | 同上 |
| S15 今日高效反馈 | 主线 TodayMinutes | 同上 |
| S20 主线超时 | 主线 TodayMinutes | 同上 |

**阈值参考**（以消息估算为基础）：

| 场景 | 原阈值（墙钟） | 新阈值（消息估算） | 说明 |
|------|---------------|-------------------|------|
| S15 高效 | 主线 > 2h | 主线 ≥ 20 条消息（≈60 分钟） | 3 分钟/条 |
| S20 超时 | 主线 > 4h | 主线 ≥ 30 条消息（≈90 分钟） | 3 分钟/条 |
| S10 失衡 | 支线 > 主线 + 30min | 支线消息数 > 主线消息数 + 2 | 约 6 分钟容差 |

## 十、设计原则总结

| 原则 | 实现 |
|------|------|
| **默认可用** | 消息估算不依赖任何额外工具，开箱即用 |
| **精度递进** | 增强方案在条件满足时自动生效，用户无感 |
| **优雅降级** | 任一方案失败时自动回退到下一级 |
| **用户无感** | 所有切换和降级在后台完成 |
| **不增加依赖** | tmux 仅作为可选增强，pflow 核心不强制依赖 |


## 十一、决策记录

### 正面论证

| 论点 | 来源 |
|------|------|
| tmux 焦点事件覆盖阅读/思考/输入全周期，精度最高 | 用户观察 |
| tmux 焦点事件的精度优于消息估算（3 分钟/条），也优于墙钟跨度（严重高估） | 分析对比 |
| tmux 焦点事件可作为可选增强，与默认方案共存 | 用户建议 |
| 分层架构使 pflow 不强制依赖 tmux，保持通用性 | 用户反思 |
| 消息估算（3 分钟/条）简单可靠，能有效判断注意力分配比例 | 分析 |
| 阈值调整后（20 条消息 ≈ 高效，30 条消息 ≈ 超时）仍能覆盖主要场景 | 分析 |
| 自动降级逻辑确保任何情况下都有合理估算值 | 方案设计 |

### 反面论证

| 论点 | 来源/评估 |
|------|-----------|
| 消息间隔聚合方案因 gap 不可预测（阅读/审阅时间可能远超 15 分钟）而失败 | 用户反馈 |
| 项目切换边界法需要明确的项目切换判断，但短时间（2 分钟）切换会造成时间误切 | 用户反馈 |
| tmux 焦点事件依赖 pflow 启动 Agent，用户通过其他方式启动时不适用 | 方案约束，已通过降级机制缓解 |
| tmux 焦点事件可能在 VSCode 内置终端中表现不稳定 | 已知限制，文档说明 |
| 多终端同时打开时焦点事件可能在不同终端间频繁切换，产生碎片化片段 | 通过过滤 < 10 秒片段缓解 |
| 3 分钟/条的估算可能低估深度工作场景（如长时间阅读设计文档） | 接受低估，因为核心判断基于相对比例 |
| 消息估算的准确度与消息发送频率强相关，可能不适用于每个 Agent | Hermes 的 message_count 需确认是否包含所有消息 |


## 十二、实施优先级

| 阶段 | 内容 | 说明 |
|------|------|------|
| **P0** | 实现消息估算方案 | 替换当前墙钟跨度，无外部依赖 |
| **P1** | 实现 tmux 焦点事件方案 | 可选增强，需注入配置和日志脚本 |
| **P2** | 实现降级逻辑 | 确保不同方案间平滑切换 |
| **P3** | 调整 suggest 阈值 | 基于消息估算的新阈值上线后观察数据分布再微调 |
