## 2. 讨论背景：信任的个性化参数根源

用户信任 pflow 的深层原因之一是：**所有参数微调都建立在自己的工作方法上，与自身习惯完美契合**（例如「一个项目闲置多久才需要被提醒」——这个阈值来自个人经验，结合部分科学数值，终究因人而异）。

推论：要让陌生用户建立同等信任，需要**让参数以某种方式可供用户参与调整**。但——

> 如果只是提供一个设置页 + 大量配置项列表，那是一种灾难：没有人会打开设置页，逐项理解并学习如何配置。

## 3. 核心思路：摩擦点内联微调（参照游戏引导）

- **来源类比**：游戏不会把设置做成列表让你一次性学完。每个小设定会在合适的时机弹出引导（「这里可以增加/减少数值」），或由 NPC 在剧情中带你完成设置。
- **核心机制**：不提供设置页列表式调参，而是在**界面交互的摩擦点**引导用户完成设置。
- **具体示例**（讨论中提出的原型）：当系统提示某个项目闲置时，在提示旁边提供微调控件：
  - 「+5 分钟」按钮（更晚提示）／「-5 分钟」按钮（更早提示）
  - 同时允许直接输入期望值
  - 用户在「这个提醒让我烦了」的当下即可调整，调整即时生效

## 4. 为什么这个模式有效（讨论中识别出的优势）

- **教学顺路**：用户在感到阈值不对的那一刻调整，正是学习成本最低的摩擦点；教学嵌入任务流本身，零额外时间成本——工具用户没耐心上「教学关」，这与游戏玩家不同。
- **参数从「抽象全局设置」变成「情境化即时决策」**：用户不必理解「闲置阈值」这个抽象概念，只需表达「太早了/太晚了」。
- **每次微调都是隐式反馈**：系统可观察用户调整方向，但不代劳。

## 5. 边界与注意（批判性审查记录）

- **兵权原则延伸**：微调动作永远留给用户，系统不得「学习后自动改参数」——否则越过 pflow「只展示、不判断」的规矩。系统只负责把参数及其效果讲清楚。
- **适用频率筛选**：内联微调适合**高感知频次**的参数（提醒阈值、等待时间等用户会反复接触的）；低频一次性参数不值得占用交互空间。哪些参数值得做，需逐个评估，不可全套内联化。
- **不打断原则**：控件应是被动的、邻近的、可忽略的，不能弹窗打断当前工作流（与「无感调度」哲学一致）。
- **防误触**：+5/-5 的步进值本身也是个参数，需考虑撤销/重置入口（「恢复默认」）。
